# TabBridge data format, version 1

This is the normative description of the version-1 snapshot, encrypted-record, and export
structures. Keywords **MUST**, **MUST NOT**, **SHOULD**, and **MAY** describe interoperability and
security requirements.

All JSON is UTF-8. Producers emit ordinary JSON with no executable semantics. Objects have exact
allowed keys; unknown keys, non-plain objects, prototype-pollution keys (`__proto__`, `prototype`,
`constructor`), non-finite/out-of-range numbers, and unsupported versions are rejected.

## Conventions

- Identifiers are lowercase/uppercase-insensitive RFC 4122-style UUID text generated by
  `crypto.randomUUID()`. They are opaque; native browser IDs are never serialized.
- Dates are ISO 8601 strings accepted by `Date.parse` and beginning with `YYYY-MM-DDT`. Producers
  emit `Date.prototype.toISOString()` values.
- Byte strings use standard padded Base64 (`A–Z`, `a–z`, `0–9`, `+`, `/`, and zero to two final `=`
  characters), not Base64url.
- Plaintext JSON is serialized with `JSON.stringify`, encoded as UTF-8, and compressed with gzip
  before encryption.
- Version 1 accepts only `http:` and `https:` tab URLs. A consumer normalizes them with the URL
  parser before capture/import/restore.

## Plaintext snapshot schema

The complete snapshot exists only in trusted extension memory before encryption or after
authenticated decryption.

```ts
interface SnapshotV1 {
  schemaVersion: 1;
  snapshotId: UUID;
  generationId: UUID;
  name: string;
  createdAt: ISODate;
  updatedAt: ISODate;
  sourceDevice: {
    id: UUID;
    label: string;
    browser: 'chrome' | 'firefox' | 'chromium' | 'unknown';
    browserVersion?: string;
    operatingSystem?: string;
  };
  windows: WindowV1[];
  captureWarnings: CaptureWarningV1[];
}

interface WindowV1 {
  id: UUID;
  order: number;
  state?: 'normal' | 'minimized' | 'maximized' | 'fullscreen';
  activeTabId?: UUID;
  groups: GroupV1[];
  tabs: TabV1[];
}

interface GroupV1 {
  id: UUID;
  title: string;
  color: 'grey' | 'blue' | 'red' | 'yellow' | 'green' | 'pink' | 'purple' | 'cyan' | 'orange';
  collapsed: boolean;
  order: number;
}

interface TabV1 {
  id: UUID;
  url: string;
  title: string;
  index: number;
  pinned: boolean;
  active: boolean;
  groupId?: UUID;
}

interface CaptureWarningV1 {
  code: 'unsupported-url' | 'private-window' | 'missing-url' | 'group-unavailable';
  message: string;
  count: number;
}
```

Within a window, tab and group references MUST resolve to objects in that window. IDs within each
collection MUST be unique. `activeTabId`, when present, MUST identify a saved tab. At most one tab
has `active: true`. Consumers sort windows by `order` and tabs by `index`; array order alone is not
the durable ordering contract. Because WebExtension group objects have no index, a producer derives
each group's `order` from the lowest saved `index` of its member tabs.

`snapshotId` is the stable logical identity. `generationId` changes whenever an operation such as
rename produces new encrypted content. Restore never changes the stored generation.

## Bounds

| Value                             | Version-1 maximum/range  |
| --------------------------------- | ------------------------ |
| Import file                       | 25 MiB UTF-8 bytes       |
| Decompressed plaintext            | 32 MiB                   |
| Generic JSON nesting              | 20 levels                |
| Windows                           | 50                       |
| Tabs per window                   | 1,000                    |
| Tabs total                        | 5,000                    |
| Groups per window                 | 250                      |
| Groups total                      | 500                      |
| Capture warnings                  | 100                      |
| Snapshot name                     | 200 UTF-16 code units    |
| Tab/group title                   | 2,000 UTF-16 code units  |
| URL                               | 16,384 UTF-16 code units |
| Device label                      | 120 UTF-16 code units    |
| Browser version / OS label        | 80 UTF-16 code units     |
| Warning message                   | 500 UTF-16 code units    |
| Encoded ciphertext                | 35 MiB characters        |
| Chunks                            | 512                      |
| PBKDF2 iterations accepted        | 600,000–2,000,000        |
| Passphrase accepted by v1 UI/core | 12–1,024 characters      |

The file-size limit is checked in UTF-8 bytes. Current schema string limits are JavaScript string
lengths, so they count UTF-16 code units. Storage quota estimates count UTF-8 bytes.

## Cryptography

Version 1 uses:

- KDF: PBKDF2-HMAC-SHA-256;
- producer work factor: exactly 600,000 iterations;
- producer salt: 16 random bytes;
- cipher: AES-256-GCM;
- IV: a fresh 12 random bytes for every encryption under a key;
- authentication tag: 128 bits, appended to ciphertext by Web Crypto;
- compression: gzip before encryption; and
- assembly digest: SHA-256 over the ciphertext-with-tag bytes.

All Base64 fields MUST use the canonical padded encoding. Version-1 salts decode to exactly 16
bytes, AES-GCM IVs to exactly 12 bytes, and SHA-256 digests to exactly 32 bytes. Ciphertext/verifier
values must contain at least the 16-byte GCM authentication tag. These bounds are checked before
PBKDF2 or AES processing.

The digest is an error/corruption check and is not a substitute for AES-GCM authentication.

For a snapshot or export, additional authenticated data is the UTF-8 encoding of this exact ASCII
construction, without a trailing newline:

```text
tabbridge-snapshot|encryption=1|schema=1|snapshot=<snapshotId>|generation=<generationId>|compression=gzip|cipher=AES-256-GCM
```

Changing the schema/encryption version, logical IDs, compression declaration, ciphertext, tag, key,
or effective IV causes authentication or subsequent consistency validation to fail. After
decryption, the embedded `snapshotId` and `generationId` MUST equal the envelope values.

Passphrases are consumed as entered and encoded as UTF-8; they are not trimmed or normalized by the
cryptographic functions.

## Vault config

The vault config is plaintext control metadata stored locally at `tb:vault:config` and optionally at
`tb:sync:vault` when Browser Sync is enabled:

```ts
interface VaultConfigV1 {
  formatVersion: 1;
  vaultId: UUID;
  kdf: {
    name: 'PBKDF2';
    hash: 'SHA-256';
    iterations: number;
    salt: Base64;
  };
  verifier: {
    iv: Base64;
    ciphertext: Base64;
  };
  createdAt: ISODate;
}
```

For newly created v1 vaults, the verifier plaintext is `TabBridge vault verifier v1:<vaultId>`. Its
AAD is:

```text
tabbridge-vault|format=1|vault=<vaultId>|cipher=AES-256-GCM
```

The verifier distinguishes a wrong passphrase without decrypting a snapshot. It is not a password
hash suitable for authentication and must not be presented as password recovery.

When supported, the trusted `storage.session` key `tb:session:vault-keys` maps vault UUIDs to Base64
raw 32-byte AES key material. This value MUST NOT be copied into local or sync storage and MUST be
removed by Lock.

## Encrypted snapshot object

The in-memory object passed between crypto and record storage is:

```ts
interface EncryptedSnapshotV1 {
  format: 'tabbridge-encrypted';
  encryptionVersion: 1;
  schemaVersion: 1;
  snapshotId: UUID;
  generationId: UUID;
  vaultId: UUID;
  compression: 'gzip';
  cipher: { name: 'AES-GCM'; keyLength: 256; iv: Base64 };
  ciphertext: Base64;
  digest: Base64; // SHA-256(ciphertext bytes)
}
```

Snapshot names, device labels, browser/OS strings, URLs, titles, groups, counts, and warnings are
not envelope fields.

## Local and sync record layout

The same record grammar is used in `storage.local` and `storage.sync`; `<ns>` is `tb:local` or
`tb:sync`:

```text
<ns>:chunk:<snapshotId>:<generationId>:<index-3-digits>
<ns>:manifest:<snapshotId>
<ns>:tombstone:<snapshotId>
```

Chunk values are substrings of the standard-Base64 ciphertext, each at most 7,000 ASCII characters.
“7,000” means encoded characters/bytes, not 7,000 raw ciphertext bytes. The final chunk can be
shorter.

The manifest is plaintext control metadata:

```ts
interface RecordManifestV1 {
  kind: 'tabbridge-record-manifest';
  formatVersion: 1;
  snapshotId: UUID;
  generationId: UUID;
  vaultId: UUID;
  schemaVersion: 1;
  encryptionVersion: 1;
  compression: 'gzip';
  cipher: { name: 'AES-GCM'; keyLength: 256; iv: Base64 };
  chunkCount: number;
  ciphertextLength: number; // Base64 character count
  digest: Base64;
  committedAt: ISODate;
}
```

Commit protocol:

1. Split the new generation and calculate exact item estimates as
   `UTF8(key).length + UTF8(JSON.stringify(value)).length`.
2. For sync, reject any projected item over 8,192 bytes, the namespace over 512 items, or the total
   over 102,400 bytes.
3. Write all new chunks.
4. Read back those exact chunk keys and compare values.
5. Publish the manifest last and read it back.
6. Reassemble exactly `chunkCount` chunks and require `ciphertextLength` and `digest` to match
   before AES-GCM authentication.
7. Only after a verified commit may obsolete generation chunks be removed.

An unreferenced chunk is never a committed record. Cleanup MUST NOT delete a potentially in-flight
remote generation merely because `storage.onChanged` delivered chunks before a manifest; maintenance
needs transaction/age knowledge.

A deletion marker is:

```ts
interface TombstoneV1 {
  kind: 'tabbridge-tombstone';
  snapshotId: UUID;
  deletedAt: ISODate;
}
```

A valid tombstone hides a manifest for the same snapshot. Tombstones can remain after data deletion
to prevent offline stale state from resurrecting.

Other local control keys include `tb:settings`, `tb:last-action`, restore cancellation state, and
the non-secret passphrase-rotation journal. `tb:sync-write-scheduler` records only the last
successful sync-mutation time so writes can be spaced by at least 2.1 seconds across background
restarts. These keys are not part of the interoperable snapshot payload.

## Export file

A `.tabbridge` file is a standalone UTF-8 JSON object with media type
`application/vnd.tabbridge+json`:

```ts
interface ExportFileV1 {
  fileFormat: 'tabbridge';
  formatVersion: 1;
  schemaVersion: 1;
  snapshotId: UUID;
  generationId: UUID;
  compression: 'gzip';
  kdf: {
    name: 'PBKDF2';
    hash: 'SHA-256';
    iterations: number;
    salt: Base64;
  };
  cipher: { name: 'AES-GCM'; keyLength: 256; iv: Base64 };
  ciphertext: Base64;
  digest: Base64;
}
```

Export derives an independent key from the export passphrase with a new random salt and uses a new
IV. The stored vault key is not serialized. The plaintext file reveals format versions, two logical
UUIDs, KDF/cipher parameters, ciphertext length, and digest; snapshot contents remain encrypted.

Import preview MUST complete all syntactic bounds, canonical encoding/cryptographic lengths,
digest/authentication, bounded decompression, migration, exact schema, ID-consistency, and
URL-policy checks before showing its counts and excluded-URL total. The user then explicitly
confirms; the commit path repeats validation before its first storage mutation. If the authenticated
snapshot ID already exists or has a tombstone, the importer assigns new snapshot/generation UUIDs
and re-encrypts it as a local copy rather than overwriting or reviving the existing record.

## Evolution and compatibility

`formatVersion`, `encryptionVersion`, and `schemaVersion` evolve independently. Version-1 readers
accept only values they explicitly implement. A future version is rejected with an
unsupported-version error rather than guessed.

Migration occurs only after authenticated decryption and before current-schema validation. Version 1
currently has no older schema to migrate. A migration MUST be deterministic, bounded, tested with
fixtures, and must not weaken URL or object-key validation.

Changing KDF parameters, AAD syntax, Base64 alphabet, compression, field names, or ordering
semantics is a format change and requires fixtures that prove Chrome/Firefox export interoperability
plus a documented compatibility path.
